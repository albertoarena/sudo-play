# AGENTS.md

## Project

**Sudo Play** is an open-source macOS menu bar app for developers.
The user picks a genre and a developer mood, and the app suggests today's Spotify playlist and plays it.

Tagline: `$ sudo play --mood friday-deploy`

- Requirements: `docs/REQUIREMENTS.md` (source of truth for WHAT to build)
- Build plan: `docs/INSTRUCTIONS.md` (source of truth for HOW and in which ORDER)

Read both before starting any work. If they conflict with this file, ask.

Three supporting files, none of them a source of truth:

- `docs/DECISIONS.md` (log of choices the plan left open, append one entry when you make one)
- `docs/QA.md` (manual checks that tests cannot cover, ticked as they pass, cleared and re-run against the signed build in M7)
- `docs/IMPROVEMENTS.md` (polish noticed while using the app: not a backlog, not a bug list, and nothing is committed to. Anything broken belongs in a milestone or a fix branch)

## Stack

- PHP 8.4+, latest Laravel version supported by NativePHP
- NativePHP Desktop (check https://nativephp.com/docs for the current package name, install steps and APIs before using them, do not rely on memory)
- Inertia + Vue 3 + **TypeScript** (`<script setup lang="ts">`) + Tailwind CSS
- SQLite (NativePHP default database)
- Pest for backend tests, Vitest and Vue Test Utils for components
- Larastan for static analysis, Pint for code style
- `vue-tsc` for type checking the frontend

## Non-negotiable rules

1. **TDD always.** Write a failing test first, run it, see it fail, then write the code to make it pass, then refactor. No production code without a test that required it. Pest for PHP, Vitest for Vue components. UI glue (NativePHP facades) is wrapped behind interfaces so the logic can be tested with fakes.
2. **No Spotify Web API.** No OAuth, no client ID, no API calls to Spotify. The app only opens public playlist links. This is a product decision, not a temporary shortcut.
3. **No accounts, no analytics, no tracking.** The only network call is downloading the public catalog file.
4. **Keep it simple.** No event sourcing, no queues, no extra packages unless a milestone in `docs/INSTRUCTIONS.md` asks for them. Plain Eloquent and plain PHP classes are fine.
5. **Stop after each milestone.** Summarise what was done, show the test results, and wait for human approval before starting the next milestone.

## Architecture

```
app/
  Catalog/         # parsing, validation, sync of the playlist catalog (pure PHP + one HTTP client)
  Rotation/        # daily pick logic (pure PHP, no framework dependencies)
  Player/          # PlayerInterface + implementations (AppleScript, open app, web)
  Notifications/   # DailyReminder, wraps NativePHP Notification behind an interface
  Http/Controllers # thin Inertia controllers only
  Providers/NativeAppServiceProvider.php  # menu bar, windows, scheduler wiring
resources/js/
  pages/           # Inertia pages (MenuBar.vue, Settings.vue), lowercase, this is where Inertia looks
  components/
  types/           # shared TypeScript types (Playlist, Mood, Genre, Settings)
catalog/
  playlists.yaml   # the community catalog, also bundled as offline fallback
tests/
  Unit/            # Catalog, Rotation, Player logic
  Feature/         # controllers, sync, settings
  fixtures/        # sample catalog files (valid and broken)
```

Business logic lives in `Catalog/` and `Rotation/` and must not depend on NativePHP. Controllers stay thin.

Settings are read and written only through `SettingsStore`. Nothing else touches a settings facade or table. Section 11 of `docs/REQUIREMENTS.md` lists the seams that keep later work possible, read it before changing an interface.

## Conventions

- Strict types in every PHP file: `declare(strict_types=1);`
- Final classes by default, readonly value objects for catalog data
- UI copy and docs: plain English, short sentences, no em dashes
- Never use the Spotify logo. Text only: "Open in Spotify". The README must say the project is not affiliated with Spotify.

## Git conventions

- Small conventional commits: `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`
- One commit per green TDD cycle is fine, do not squash everything at the end
- Commit format: `type: short subject` (max 50 chars), then a body paragraph explaining what and why, not how
- Use a heredoc for multi-line commit messages
- Never attribute commits or pull requests to Claude Code, Codex or any other tool. No "Generated with Claude Code", no `Co-Authored-By` trailer for a tool
- This covers the pull request description, not only the commit message. Some tools append a footer such as `_Generated by Claude Code_` with a session link when the pull request is opened. The model does not write that line, the tool does. Remove it from the description before asking for review
- On a local machine, configuration fixes it. Carry `"attribution": { "commit": "", "pr": "", "commitTrailers": false, "sessionUrl": false }` in `~/.claude/settings.json`
- Configuration does not fix it in a cloud session. There the footer is added by the session's egress proxy on the way out: a raw `curl` sending a clean body gets it back with the footer attached, so no settings file inside the container removes it. A committed `.claude/settings.json` does not either, because attribution is not read from project settings
- So a pull request opened from a cloud session needs its description checked, and the footer stripped afterwards from a machine outside that proxy. Either edit it in the GitHub web interface, or `gh api -X PATCH repos/<owner>/<repo>/pulls/<number>` with the corrected body
- Commits are authored by the repository owner, not by the tool. A cloud container can ship a global git identity of `Claude <noreply@anthropic.com>`, which every commit then inherits as author and committer. Set `git config user.name` and `git config user.email` before the first commit, and verify with `git log -1 --format='%an <%ae>'`
- That is a different mechanism from the attribution rules above, which govern message text only. A commit message can be perfectly clean while the author is wrong, so checking one says nothing about the other. M3 failed exactly this way
- Every commit goes through a pull request, never straight to `main`
- Only exception: a commit that touches markdown files only can go straight to `main`
- `main` gets branch protection in M7, with `ci.yml` as the required check. It is not protected yet: the repository is private, and protection on a private repository needs a paid plan, so it waits for the milestone that makes it public
- Until then nothing enforces any of this. Never push to `main` and never merge your own pull request because these rules say so, not because GitHub would stop you. It would not
- Releases are tags on `main` (`vMAJOR.MINOR.PATCH`). There is no release branch. See `docs/REQUIREMENTS.md` section 12 and `docs/RELEASE.md`
- Never commit a version bump. The version comes from the tag at build time

## Working as an agent

These rules keep the human in the loop. Follow them even when you have the access to do otherwise.

- One milestone, one branch, one pull request. Name the branch after the milestone: `feat/m1-catalog-parsing`
- Commit per green TDD cycle on that branch. When the milestone is done, push the branch, open the pull request, then stop
- **Never merge your own pull request.** A human reviews and merges it. Never push to `main`
- The markdown-only exception in the git conventions does not apply inside a code milestone. Documentation that belongs to a milestone goes in that milestone's pull request, not straight to `main`
- Tick the Status box in `docs/INSTRUCTIONS.md` as part of the milestone's pull request. It becomes true when the pull request is merged, not when you write it
- If a step cannot be run in your environment, stop and say so in the summary. Anything needing macOS, a visible window, real AppleScript, a signed build or the checks in `docs/QA.md` falls in this group. Never skip a check silently, and never report one as passed that you did not run
- If the requirements and the build plan disagree, or NativePHP does not support something, stop and ask. Do not invent a workaround

## Working in a cloud container

Milestones run as Claude Cloud sessions in a Linux container. It is a different
machine and almost nothing about it matches the Mac. What follows is
established, not guessed: every line cost a session time before it was written
down. Treat it as fact and do not spend a milestone rediscovering it.

- **There is no macOS.** No menu bar, no notification centre, no login items, no
  `native:serve`, no AppleScript, no Automation prompt. Anything needing those
  is written into `docs/QA.md` for a human to run, and is never reported as
  verified here
- **PHP is 8.3, the project needs 8.4.** Install with
  `--ignore-platform-req=php`. The ondrej PPA, php.net, Docker and static builds
  are all blocked. One session installed 8.4 through nix and one found nix
  blocked too, so try nix once if you wish and drop it the moment it resists.
  Try nothing else. CI runs 8.4 and is the real check
- **GitHub downloads are permitted only for this repository.** The refusal reads
  "GitHub access to this repository is not enabled for this session", and it is
  the session's repository authorization, not a network rule, so no token
  changes it. Composer therefore cannot fetch package zips and falls back to
  cloning from git, which is slow. `nativephp/php-bin` is a very long clone, and
  `phpstan/phpstan` has no git source at all and needs a zip built from its tag.
  Start the install in the background and read the codebase while it runs
- **Attach the repository with `add_repo` before the first commit**, not before
  the push. The tool is often absent at startup and appears part way through, so
  if it is not there yet, check again before pushing
- **`gh pr create` fails**, because GitHub GraphQL is blocked here. Open pull
  requests with `gh api ... /pulls`
- **The egress proxy appends an attribution footer** to a pull request
  description, and nothing inside the session removes it: a raw `curl` sending a
  clean body gets it back with the footer attached. Say in your summary that it
  is there. It is stripped from outside the session
- **Check authorship before the first commit** with
  `git log -1 --format='%an <%ae>'`. Not `git config user.name`, which reads
  `.gitconfig` and shows the container default even when the commits are correct
- **Two setup gotchas**: `php artisan key:generate` must run after `vendor`
  exists, and PHP's default 128M memory limit is too low for PHPStan here

## Definition of done (every milestone)

- All tests green, no skipped tests
- `composer analyse`, `composer lint`, `npm test`, `npm run typecheck` pass
- New behaviour is covered by tests written before the code
- Any choice the plan left open is logged in `docs/DECISIONS.md`
- The milestone is ticked in the Status list in `docs/INSTRUCTIONS.md`
- Short summary posted for review, then wait
